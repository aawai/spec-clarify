# spec-clarify 审核文档约定

[spec-clarify](https://github.com/aawai/spec-clarify) 把一份或多份 Markdown 审核文档拆成条目，交给产品方逐条澄清并保留记录。站点按**条目编号**保存澄清记录，按**条目内容**判断澄清是否过期。下面的约定保证解析成功、编号稳定、引用可以跳转。

## 文档结构

```md
# 任意标题（不解析）

前言、阅读说明等任意内容（不解析）。

## 分组标题

分组说明（不解析）。

### <编号> <条目标题>

- 严重度：高
- 文档：specs/login.md
- 相关：A2、B1
- 建议：补充锁定时长

正文 Markdown：问题描述、依据、影响。可以包含列表、表格、代码块。
```

- `##` 开启一个分组；分组标题在文档内唯一，它同时是站点筛选用的键。
- 分组内每个 `###` 标题是一个条目，必须写成 `### <编号> <标题>`，编号和标题之间用空格分隔。
- 第一个 `##` 之前的内容、分组标题与第一个条目之间的内容都不会成为条目，可以写说明文字。
- `####` 及更深的标题属于条目正文。代码块里的 `#` 不会被解析。
- 条目从 `###` 一直延续到下一个 `##` 或 `###`。

## 编号

- 格式：英文字母开头，只含英文字母、数字、`_`、`-`，例如 `L1`、`login-03`、`AUTH_2`。不能含中文、`.` 或空格。
- 在站点的**所有**审核文档中唯一（一个站点可配置多份审核文档）；重复时站点拒绝加载，并指出两处位置。新建审核文档前，先查看配置的 `reviews` 里已有文档用过的编号前缀，换一个不冲突的前缀。
- **编号一经发布就不再改动或复用**。澄清记录挂在编号上：改号会让记录挂错条目；删掉的条目，其历史记录只出现在导出文件的“已从审核文档移除的条目”一节。
- 新增条目用新编号，追加在分组末尾或任意位置均可，不要为了连续而给已有条目重新编号。
- 推荐“分组前缀 + 序号”，例如登录模块用 `L1`、`L2`……，跨模块问题用 `C1`、`C2`……

## 元数据列表

紧跟在条目标题后（中间可以空行）的连续 `- 键：值` 列表是元数据；冒号可用全角 `：` 或半角 `:`。列表后的第一个空行或任何其他行开始正文，正文中的列表不再当作元数据。

| 键                    | 含义                                                                                      |
| --------------------- | ----------------------------------------------------------------------------------------- |
| `严重度` / `severity` | 严重度，取值应出现在配置的 `severities` 中，站点按其顺序着色和排序筛选项                  |
| `文档` / `document`   | 本条目里不带文件名的 `:行号` 引用指向的文档                                               |
| `相关` / `related`    | 相关条目编号，用 `、`、`，` 或空格分隔；不存在的编号会被忽略                              |
| 其他任意键（≤20 字）  | 作为字段显示在“审核意见”中（值支持行内 Markdown 与行号引用），例如 `建议`、`位置`、`维度` |

正文开头如果恰好是 `- 某某：…` 形式的列表，在它前面先写一行普通文字，避免被识别成元数据。

## 行号引用

站点把审核文本里的行号引用链接到源文档对应行并高亮：

| 写法                   | 指向                                                                                   |
| ---------------------- | -------------------------------------------------------------------------------------- |
| `specs/login.md:12`    | 该文件第 12 行；也可只写文件名 `login.md:12`，前提是文件名在所有文档中唯一             |
| `specs/v1/login.md:12` | 指定修订版第 12 行（可用 `v1/login.md:12` 或 `@/specs/v1/login.md:12`）                |
| `specs/login.md`       | 不带行号的文档或修订版路径（如 `specs/v1/login.md`、`@/specs/login.md`、唯一短文件名） |
| `:12`                  | 本条目 `文档` 元数据指定的文件；同一句里出现过显式文件后，改指向该文件                 |
| `:12–20` 或 `:12-20`   | 行范围                                                                                 |
| `:12、15、20–22`       | 同一文件的多处                                                                         |
| `图@:12`               | 带标签的引用（标签 1–4 字符，也可写 `图@login.md:12`），标签原样显示在链接中           |

- `；`、`;` 或段落结束时重置上下文，之后的 `:行号` 回到条目默认文档；无行号文档引用也会把当前分句后续 `:行号` 切到该文件。
- 行号是**源文件的物理行号**（编辑器左侧行号），不是渲染后的段落序号；引用前先打开文件核对。
- 超出文件行数、找不到文件或文件名不唯一的引用保持纯文本，不会报错，因此要自行核对。
- 行内代码和已有 Markdown 链接内的引用不会被链接。

## 修订已有审核文档

- 可以修订条目、追加条目、调整条目顺序或所属分组；记录只认编号，这些都不影响已有记录。不要重编号。
- 修改条目的标题、`严重度`、`文档`、其他字段或正文后，已澄清的条目会被标为“需复核”，提示产品方重新确认；只调整空白、换行或表格对齐不会触发，修改 `相关` 也不会。修错字同样会触发，因此尽量一次改完。
- 删除条目不会删除它的记录，但站点页面上不再显示；历史只出现在导出文件的“已从审核文档移除的条目”一节。

## 项目配置

审核文档放在项目里，旁边写一份 `spec-clarify.config.json`（所有路径相对于配置文件）：

```json
{
  "title": "某某需求澄清",
  "documents": ["specs/**/*.md"],
  "reviews": [
    { "path": "docs/review.md", "title": "产品审核" },
    { "path": "docs/security-review.md", "title": "安全审核" }
  ],
  "severities": ["阻塞", "高", "中", "低"],
  "database": "data/spec-clarify.db"
}
```

- `reviews`：本站点澄清的审核文档，至少一项。`title` 默认取文档的 `#` 一级标题；有多份时，导航和导出按它把分组归到各自文档下。`adapter` 默认 `markdown`（另有兼容中文 PRD 审核报告的 `prd-review`，配 `options`）。新增审核文档只需在列表中追加一项，已有记录不受影响。`相关` 可以引用其他审核文档的条目。
- `documents`：被引用的源文档 glob；审核文档本身自动加入文档列表。
- `revisions`：可选的源文档修订集（每项含 `id`、`label`、`dir`），按稀疏覆盖方式存放修订版或新增文档；`id` 限英文字母、数字、`_`、`-` 且唯一，`dir` 须在项目内且不与 `reviews` 或其他修订目录重叠；短文件名始终只匹配基线文档，不影响历史行号引用。
- `trustDocumentHtml`：源文档含需要渲染的 HTML（如 `<font>`、`<img>`）且内容可信时设为 `true`，默认按纯文本显示 HTML。
- `allowExternalImages`：源文档引用外部图片时设为 `true`。
- 配置校验为严格模式，不接受未定义字段。

## 写好一个条目

- 一个条目只提一个需要产品决定的问题；多个问题拆成多个条目，用 `相关` 关联。
- 标题写成问题本身（“锁定时长未定义”），不要写成“问题 1”。
- 正文先给证据（带行号引用），再说影响，最后可在 `建议` 字段给出候选方案，方便产品直接选择。
- 区分事实与推断，推断明确标注。

## 校验

写完或修改后运行：

```sh
npx spec-clarify check --config spec-clarify.config.json
```

输出每个分组的条目数；配置错误、源文档/修订目录不可读或格式错误（缺编号、编号重复、分组标题重复、条目不在分组内）都会报错并以非零状态退出，格式错误会给出行号。该命令不校验正文内 `文件:行号` 是否存在或越界。站点运行中遇到同样的错误会暂停查看与提交，直到文档修复。

## 读取澄清结论与版本差异（MCP）

若当前环境已配置 `spec-clarify` MCP（本地 `npx spec-clarify mcp` 或远程 `/mcp`），修订审核文档或回填澄清结果时优先使用 `list_items` / `get_item` 查询已澄清结论与待回复讨论，使用 `list_documents` / `get_document` / `diff_document` 获取修订版变化与纯文本 Unified Diff，无需人工导出或手工翻目录比对。

多批澄清场景下，可传入 `list_items(status="clarified", applied=false)`（或 `afterClarificationId` 游标）仅拉取尚未落地处理的澄清；处理完成后通过 MCP `resolve_items`（需开启 `--write` / `--mcp-write`）或命令行 `npx spec-clarify ack <编号...> --clarification <latestClarification.id> --by ai` 记录已落地，避免后续会话重复处理。若产品提交了更新的澄清，条目会自动重新回到 `applied=false`。
